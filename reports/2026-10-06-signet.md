Completed October 6, 2026 UTC (October 5 in America/Denver).
Implementation: `7401257b09a1b407e4502db2a6ceb9f6c907d9bc`.

**Result: the shared-balance contract opened, changed allocations off-chain,
superseded a deliberately stale on-chain state, and unilaterally settled the
latest balances on an experimental signet.** This is a development channel contract;
BOLT Lightning routing and pending HTLC exits are not implemented.

## What happened

1. A test wallet funded a 301,000-sat channel output. All three participants had
   durable opening recovery information before funding was broadcast.
2. Three separate signing processes approved and journaled two off-chain updates:
   100,000/100,000/100,000 became 95,000/100,000/105,000, then
   95,000/103,000/102,000.
3. The test deliberately broadcast the older update. It confirmed in block 457.
4. Recovery used the existing signatures for the newer update, without asking
   channel signers to sign again. The override confirmed in block 458.
5. A bounded watcher followed the chain, waited the 12-block contest delay, and
   broadcast settlement. Block 470 paid **95,000, 103,000 and 102,000 test sats**.

No IBD was started, and no real coins or production wallet keys were used.
The temporary watcher finished successfully. Payout keys remain in the private
test runtime; no keys or recovery secrets are included in this repository.

## How recovery works

Each state output has two Taproot paths: a newer, three-signature update, or a
fixed payout after 12 blocks. TEMPLATEHASH commits to the new output and state
number. CLTV requires that number to increase; CSV delays final settlement so an
observer can supersede a stale state. A fresh fee input pays for each override
without reducing channel balances. CSFS messages are 32 bytes; conventional fee
signatures and funding use unified sighash. No new feature bits are assigned.

This is contest-based protection: somebody must monitor and get an override
confirmed in time. It does not make indefinite offline operation safe.

## Validation

- CI run `37404362908`: ten accounting tests and five channel/signer tests passed.
- [Private regtest](2026-10-06-contest-regtest.json): restart recovery, incomplete
  signatures, conflicting proposals, interrupted rounds, invalid old-state
  spends, CSV timing and a shallow maturity reorg passed.
- Regtest replaced both a stale update and a stale settlement in the mempool.
  Replacing a late settlement is best effort, not a substitute for timely monitoring.
- Experimental signet: opening, two signed allocations, confirmed stale-state override,
  autonomous final payout and verified payout amounts passed.

Funding used a 1 sat/vB fee. Updates used 1,000 and 2,000 sats from separate fee
coins; settlement used the channel's 1,000-sat reserve. Exact funding fee and
transaction sizes are in the JSON report. These are fixed demonstration fees,
not an optimized fee estimator.

The tested node was revision `2f142fdd75719d23046be5b1577fc9ef280f3dc3`.
It predates the configurable CSFS cap. All test messages were 32 bytes, but this
run does not claim to test cap enforcement on that older node. No relay policy
overrides were introduced. Recommended source and tested binary revisions are
both recorded in dependencies.lock.json.

## Limits and remaining work

All three processes ran on one administrative host, with one test-wallet-funded
opening transaction. There is no BOLT invoice routing, conditional HTLC exit
implementation, atomic multi-party funding, or production-grade watchtower.
Adversarial fee pressure, deep reorgs, pinning and authenticated distributed
agreement need further work. The fixed-fee settlement has no integrated CPFP
manager. Python functional-test cryptography must not protect real funds.
